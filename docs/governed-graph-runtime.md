# Hermes Governed Graph Runtime

The governed graph runtime executes dependency-aware Hermes workflows without giving model workers authority over trust, policy, provenance, or merge decisions.

## Authority chain

```text
plan
  -> fake-edge and contract validation
  -> resource/cost governor
  -> trust/classification gate
  -> bounded scheduler
  -> worker candidate output
  -> schema verification
  -> provenance verification
  -> trust/classification verification
  -> evidence verification
  -> policy verification
  -> deterministic fan-in
  -> checkpoint + telemetry
```

Workers produce candidates. Only the runtime creates dependency lineage hashes and decides whether output is accepted into the graph.

## Files

- `src/system/governed_graph_runtime.py` — standard-library runtime and non-executing analyzer.
- `src/system/governed-graph-runtime.sh` — CLI wrapper.
- `config/governed-graph-runtime.json` — concurrency, provider, cost, token, and parallelism policy.
- `config/governed-graph-plan.schema.json` — external plan contract.
- `config/governed-graph-plan.example.json` — reference topology.
- `tests/test_governed_graph_runtime.py` — runtime invariants.
- `tests/test_governed_graph_runtime.sh` — repository verification gate.

## Fake-edge analysis

A `data` edge without bindings does not transmit data, authority, or required ordering. The analyzer therefore treats it as a false dependency and prunes it before cycle analysis and scheduling.

`authority` and `order` edges are never pruned. Authority edges are required by contract and fail closed.

Example:

```json
{"id":"fake-a-b","source":"research_a","target":"research_b","kind":"data","bindings":{},"required":true}
```

is removed, allowing `research_a` and `research_b` to run concurrently when the resource governor says parallelism is worthwhile.

## Typed edge contracts

Data edges bind a source JSON path to a target input field:

```json
{
  "id": "a-merge",
  "source": "research_a",
  "target": "merge",
  "kind": "data",
  "bindings": {"finding_a": "$.finding"},
  "required": true
}
```

The runtime rejects duplicate writers, undeclared target fields when `additionalProperties` is false, invalid paths, cycles, unknown nodes, self-dependencies, and unsupported edge types before executing workers.

At runtime each node input and output is validated against a conservative JSON-Schema subset: object/array/string/boolean/integer/number/null types, required properties, properties, additional properties, enum, const, `allOf`, `anyOf`, item schemas, length/item limits, regex patterns, and numeric minimum/maximum.

## Handler API

Register handlers by the `handler` name declared on each node. A handler receives a `NodeContext` containing:

- its immutable node specification;
- validated bound inputs;
- accepted predecessor outputs in deterministic node-id order;
- `dependency_status`, including optional predecessor failures;
- the effective graph hash;
- the bounded retry attempt number.

Handlers may return ordinary JSON-compatible data or `NodeOutput` when they need to attach evidence, classification, measured cost, measured tokens, or external provenance.

A worker-supplied classification is still checked against the node ceiling. It does not grant trust.

## Trust and provenance

Hermes classifications are enforced with the same fail-closed categories used elsewhere in the system:

- `PUBLIC`
- `INTERNAL`
- `CONFIDENTIAL`
- `LEGAL_PRIVILEGED`
- `FINANCIAL`
- `SECURITY_SENSITIVE`
- `CREDENTIAL`

For example, `LEGAL_PRIVILEGED` data cannot flow into an `INTERNAL` node.

Accepted output lineage is generated by the runtime from verified predecessor hashes. A worker cannot manufacture dependency lineage simply by returning a success flag.

Every accepted node output receives a deterministic SHA-256 content hash covering data, evidence, classification, measured cost/tokens, external provenance, and dependency provenance.

## Verification order

Before a candidate may enter fan-in, Hermes applies:

1. output schema validation;
2. output classification/trust validation;
3. evidence requirement, when configured;
4. provenance normalization and runtime lineage generation;
5. optional deterministic policy verifier.

A verification failure is terminal for that candidate and is counted by stage in telemetry. It is not retried as though it were a transient provider failure.

Required downstream nodes are blocked when a required predecessor is failed or rejected.

## Parallel scheduler and cost control

The resource policy supports:

- global maximum concurrency;
- per-provider concurrency limits;
- estimated graph cost ceiling;
- estimated graph token ceiling;
- minimum estimated latency savings required before parallel execution;
- coordination overhead;
- verification overhead.

The runtime parallelizes a ready set only when the estimated latency savings minus configured coordination and verification overhead meet the configured threshold. Otherwise it deliberately executes ready nodes serially.

Limits are strict positive integers. Fractional concurrency values are rejected rather than silently truncated.

## Deterministic fan-in and optional branches

Fan-in is ordered by node id and edge id, not by completion timing.

An optional failed branch does not block a downstream node, but its failure is exposed in `NodeContext.dependency_status`. It is never silently omitted from the control plane.

Run status is:

- `success` — all graph nodes succeeded;
- `degraded` — one or more non-required branches failed, but all terminal sink nodes succeeded;
- `failed` — at least one terminal sink is not accepted.

## Checkpoint and resume

`FileCheckpointStore` stores only verified successful node outputs. Checkpoints are scoped by:

- effective graph hash;
- node id;
- input hash, including accepted dependency hashes.

Writes are atomic and fsynced. On reuse, the stored output hash is recomputed. A modified or malformed checkpoint is ignored and the node executes again.

Changing the graph contract changes the graph hash and invalidates stale checkpoints automatically.


## Execution-state ledger and long-horizon continuation

The runtime can receive an `ExecutionStateLedger` and `DurableTaskStateStore`. The ledger tracks deterministic observations, mutations, attempts, and state-scoped reusable successes outside model context. Reuse is explicit at graph level with `metadata.execution_state_reusable=true`; ordinary nodes continue executing normally.

Plans may declare `metadata.long_horizon` with a stable task id, objective, and requirement list. Evidence-required nodes can declare `metadata.completes_requirement`. Only output that has already passed the normal Hermes verification chain is admitted to durable progress. Rejected or failed attempts are retained without marking the requirement complete.

Before each actual handler attempt, `NodeContext.continuation_state` is rebuilt from the compact durable task record rather than from an accumulated conversation transcript. `NodeContext.execution_state` contains the bounded current execution-state snapshot. See `docs/execution-state-ledger.md` for the full contract.

## Telemetry

Each run records:

- original and effective graph hashes;
- pruned false-edge ids;
- wall-clock duration;
- measured critical-path duration;
- peak parallelism;
- blocked wait time per node;
- retries;
- rejected outputs;
- checkpoint hits;
- execution-state reuse hits;
- verification failures by stage;
- estimated and measured cost;
- estimated and measured tokens;
- per-node provider, timing, status, input hash, and output hash/provenance.

## CLI

Validation and analysis are deliberately non-executing:

```bash
src/system/governed-graph-runtime.sh validate \
  --plan config/governed-graph-plan.example.json \
  --resource-policy config/governed-graph-runtime.json

src/system/governed-graph-runtime.sh analyze \
  --plan config/governed-graph-plan.example.json \
  --resource-policy config/governed-graph-runtime.json
```

The example graph contains a deliberate false edge. Analysis should report `fake-a-b` as pruned and place `research_a` and `research_b` in the same executable layer.

## Verification

Run the focused gate:

```bash
bash tests/test_governed_graph_runtime.sh
```

The same gate runs in GitHub Actions on the feature branch and on pull requests into `hermes-max-setup`.

The gate checks syntax, JSON validity, the Python unit suite, fake-edge optimization, parallel topology, resource ceilings, and fail-closed cycle rejection.
